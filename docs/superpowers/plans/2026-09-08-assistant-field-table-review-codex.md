2. **[P1] The shared span/index contract needs grammar validation, decoded-key matching, and a duplicate-key policy before it is safe to edit.** Plan §3.1, lines 103–132 and 159–163; §7 splice mitigation; `web/src/assist/jsonText.ts:13–42`, `75–89`, `99–109`, `155–164`.

   Tokenization and bracket depth are not JSON validation. Direct calls to the current tokenizer accept `{"x":01}`, `{"x":true false}`, `{"x":1,}`, `{"x":1} trailing`, `{"x":/*comment*/1}`, an invalid `"\q"` escape, and mismatched `[1}}`. Retokenizing the output therefore cannot prove that an edit produced one JSON value. The existing API's `assertOneJsonObject` rejects malformed/trailing input before fetch, so this is an editor-integrity failure, not evidence that the current write helper leaks envelope siblings.

   Key lookup compares raw token spelling with `JSON.stringify(segment)`. For `{"rules":[{"fields":{"\u0078":{"literal":1.0}}}]}`, the structure index sees field `x`, but `lineFor(..., 'rules[0].fields.x.literal')` returns null. With duplicate `x` members on separate lines, `JSON.parse` returns the last value while `lineFor` locates the first. Escaped equivalent spellings also form duplicates. Preserving both occurrences while showing/editing only one silently splits the view from server semantics.

   **Required change:** define a complete single-value grammar check, including legal scalars/escapes, matching delimiter types, separators and EOF except JSON whitespace. Decode string keys for comparison while retaining their original spans. Detect duplicate decoded keys at every depth and send affected documents/sections to repair rather than selecting an occurrence implicitly; reject rename collisions too. Specify spans as **UTF-16 code-unit offsets**, matching JS `slice`, not byte offsets: after `{"é😀":0,` the next token starts at code-unit 9 but UTF-8 byte 12. Add direct tests for these reproductions, CRLF/tabs/compact/empty containers, trailing whitespace versus trailing content, escaped key edits (not just a neighboring edit), and non-ASCII before edited spans.

3. **[P1] Sorting edit spans right-to-left does not define an atomic multi-edit operation.** Plan §3.1, lines 110–126; §3.2 source switching and rule renaming.

   The specified removal spans can overlap: in `{"a":1,"b":2,"c":3}`, deleting middle `b` consumes its following comma and deleting last `c` consumes that same comma. Descending starts alone cannot apply both correctly. Two absent-member sets in `{}` share an insertion offset and each needs separator planning. Creating `unit` and setting `unit.from` in one batch needs a rule for paths whose parent did not exist in the input. Rename-plus-child-edit, repeated edits of one path, and array index changes also lack defined semantics. These are operations the proposed UI will generate, not exotic API consumers.

   **Required change:** specify whether paths address the original snapshot or successive intermediate documents. Implement a structural batch planner that coalesces sibling insertions/deletions and detects conflicting/overlapping operations, or explicitly resolve each operation against the intermediate text with well-defined order. Validate the complete result and commit it once through `editDocument`; failure must leave text, version, undo and gates untouched. Test adjacent/all-member removals, simultaneous insertions, missing parents, array moves, rename collisions, rename plus reference updates, and overlapping parent/child edits. Preserve the raw text of moved values; do not serialize their parsed structures.
