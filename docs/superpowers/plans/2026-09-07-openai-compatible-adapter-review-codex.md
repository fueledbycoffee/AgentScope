# Codex review: OpenAI-compatible adapter plan (issue #14)

Reviewed against ADR-005 including its amendment, the merged #13 plan including revision 3, the application port/DTOs/use case, existing LLM adapters, settings/container, import-linter configuration and API contract. References below are repository-relative; “plan” means `docs/superpowers/plans/2026-09-07-openai-compatible-adapter.md`.

This was an offline review. No endpoint was called and no credentials were used. Small local probes used the installed `httpx2` 2.12.0 and application code. The basic system/user chat-completions request is a reasonable starting point for the three targets; neither that shape nor MockTransport success establishes compatibility with a particular deployed model/server version.

1. **P1 — The HTTP client is missing from production dependencies.**

   Plan §§1, 4 and 7 introduce a runtime HTTP adapter without a dependency/lockfile change. `backend/pyproject.toml:8` omits `httpx2` from project dependencies; it exists only in the development group at line 25. A production installation without development dependencies can fail importing the compatible adapter, potentially during container import even when the assistant is disabled. CI installs all groups and would conceal this failure.

   **Fix:** Add `httpx2>=2.12.0` to runtime dependencies in `backend/pyproject.toml`, update `backend/uv.lock`, and use the actual `httpx2` import name throughout infrastructure and transport tests. Include a production-dependency installation/import/startup check in the implementation plan, using available offline artifacts where necessary. Do not substitute `httpx` or introduce a vendor SDK.

2. **P1 — SecretStr and generic redaction do not enforce the promised secret boundary.**

   Plan lines 59–79 promise that the key never appears in messages or replies, but quote provider bodies after unspecified redaction and copy provider `content` and `model` directly. A server can echo an arbitrary local key in any of those fields. `SecretStr` only protects representations of the settings value; it does not scrub provider output. The existing redactor retained the synthetic string `local-credential-canary-7319` in a local probe. `RunAssistant._call` only generically redacts errors (`backend/src/agentscope_app/application/use_cases/assistant.py:319`); `model` reaches diagnostics directly at line 311, and proposal fields originate from the unsanitised envelope at lines 374–388. The smoke script's “redacting nothing further” rationale is therefore wrong for returned metadata too.

   **Fix:** In the planned `infrastructure/llm/openai_compatible.py`, use fixed error messages with allowlisted status/host information rather than provider-body excerpts. Explicitly protect against the configured key in every returned string, including decoded content and model metadata; reject a contaminated reply with a fixed error rather than altering an executable mapping. Account for JSON escapes inside generated JSON. Never format raw request/response objects, headers or transport exception text, and suppress unsafe exception chaining. Validate URL configuration so userinfo/query credentials cannot enter diagnostic URLs. Add synthetic arbitrary-key and recognisable-key canaries echoed in errors, content, model, escaped JSON and transport exceptions; assert absence from exception strings/tracebacks, captured logs, API responses and smoke stdout/stderr. Keep secret-aware handling in infrastructure; do not pass the credential into application/domain sanitizers.

3. **P1 — Retrying generation POSTs on gateway errors contradicts the two-generation guarantee.**

   Plan lines 80–83 retry `502/503/504` twice inside each `complete`. A gateway error can occur after the upstream accepted or completed a generation; no reply reaching this client does not establish that generation never happened. One application call could initiate three generations, followed by three more during repair. `RunAssistant` counts only port invocations (`assistant.py:288–294`), whereas the merged #13 plan §4 and `docs/api/v0.1.md` promise at most two generation calls. The negotiation exception described for a rejected `400` does not justify these ambiguous replays.

   **Fix:** Preserve the accepted contract by removing automatic replays after ambiguous generation failures. Permit a narrowly recognised parameter rejection before generation to negotiate once; define any rate-limit retry separately and conservatively. If broader retries are desired, explicitly revise the generation/cost guarantee in the ADR amendment, #13 contract and API documentation before implementation. Define a single maximum HTTP-attempt budget per `complete`, shared by negotiation and any permitted retries, and distinguish it from the application's one-or-two generation attempts. Test exact transport counts for negotiation, exhaustion, first-call failure and repair failure; no transport failure should independently trigger an application repair.

4. **P1 — The stated timeout is not a total elapsed-time bound.**

   Plan lines 80–83 equate a 60-second read timeout and 10-second connect timeout with a 60-second total limit. In the supplied client API, these are phase/inactivity timeouts. A local probe showed `Timeout(60, connect=10)` also configures write and pool timeouts to 60 seconds. Connections, writes, repeated reads, backoff, negotiation and repair can accumulate beyond the claimed limit; a response that keeps delivering bytes can outlast the read timeout indefinitely.

   **Fix:** Specify whether `AGENTSCOPE_LLM_TIMEOUT_S` bounds one `complete` or the entire user operation, and state the resulting worst case for a repair. Implement a monotonic deadline covering every permitted HTTP attempt and wait, with explicit connect/read/write/pool limits capped by remaining time. The transport must actually stop at the deadline; merely checking the clock between attempts, or timing out a worker while its request continues, is insufficient. Bound response reading as well. If a hard deadline is not implemented, rename/document the setting as an inactivity timeout and remove the total-time promise. Respect a valid `Retry-After` within the remaining budget or fail rather than retrying earlier. Use an injected clock/sleeper and deterministic timeout exceptions: MockTransport does not enforce real socket timeouts by sleeping in its handler.

5. **P2 — The refusal rules misclassify ordinary empty output and leave null/precedence ambiguous.**

   Plan lines 66–69 treat an empty `content` with `stop` as refusal and refer simply to “a refusal field.” OpenAI-style responses can include `refusal: null` on ordinary successful messages; field presence must not trigger refusal. Empty output alone is not evidence of a safety refusal. The difference changes application behavior: the local probe confirmed `AssistantReply('', model, 'stop')` is repairable malformed output, while the same text with `finish='refusal'` is terminal with no repair. Content may also be null on a filtered or truncated response, so checking its type before the finish/refusal signals can lose the correct classification.

   **Fix:** Define an ordered decision table in `openai_compatible.py`: a nonempty, correctly typed explicit refusal or `content_filter` is terminal refusal; `refusal: null` is ignored; `length` stays truncated even with absent text; an empty string with `stop` reaches the application's envelope parser for its one repair. Explicitly define null/missing content without a finish/refusal explanation as malformed transport shape, and reject unsupported tool/function finishes without executing anything. Test null and nonempty refusals, refusal alongside plausible mapping text, empty stop, null length, unknown finishes and refusal on the repair call. Refusal must never yield a proposal or another repair.

6. **P2 — JSON-mode negotiation can downgrade on the wrong error and corrupt model audit metadata.**

   Plan lines 49–58 use any `400` mentioning `response_format` as evidence that the feature is unsupported. A malformed parameter value or a missing JSON instruction can mention that parameter too; silently disabling it masks a request bug. “Remembers the choice for the process lifetime” does not specify isolation between adapter instances, endpoints and models, although support may vary by all three. Appending `#no-json-mode` to `AssistantReply.model` also replaces the actual model identifier with an invented one that flows into both proposal and diagnostics.

   **Fix:** Recognise a small, tested set of explicit unsupported-parameter/capability errors, using structured fields where available, and do not downgrade on an unrelated `400`, successful non-JSON model output, refusal or truncation. Specify behavior for unrecognised rejections and leave `off` as the manual compatibility escape hatch. Cache a confirmed fallback per immutable adapter configuration (endpoint and model), with defined concurrency behavior. Test `on` never falling back, `off` never sending the parameter, auto rejection then malformed output then one application repair, unrelated errors, repeated rejection and cache isolation. Keep `model` accurate; use a safe operational event for negotiation, or deliberately add an application-owned metadata field if it must appear in the API. Do not claim `on` proves the server actually enforced JSON output.

7. **P2 — Response-shape and transport-error mapping are not exhaustive enough to protect the port.**

   Plan §3 covers missing `choices` but not `choices: []`, null/scalar top-level JSON, non-object choices/messages, list-valued content or invalid model types. Those shapes can escape as `IndexError`, `TypeError` or `AttributeError`. Ordinary non-negotiation `400`, `402`, `422`, redirects, connect/write/pool timeouts and protocol/read failures also lack an explicit terminal mapping. A `404` alone cannot prove the route is missing: a server can return it for an unknown model. The application catches only `AssistantError`, and its API status map only handles application exceptions, so leaks can become unstructured 500s (`assistant.py:319`; `interfaces/api/main.py:43,94`).

   **Fix:** Validate the chat-completions transport envelope and field types in infrastructure before indexing, while leaving parsing of the mapping text to `RunAssistant`. Classify HTTP status before decoding an error body so an HTML `401` still maps to unavailable. Specify safe defaults for every other non-success status, a redirects policy, and all relevant `httpx2` exception families; map every timeout phase to `timeout`. Handle provider error envelopes as failures, including errors in successful HTTP responses, without treating them as mapping candidates. Phrase an ambiguous `404` diagnostic as “check endpoint and model.” Add a parameterised MockTransport/API matrix including these cases, asserting application-owned errors, correct `502`/`503` envelopes and no accidental application repair for adapter errors.

8. **P2 — Startup independence is specified only for an empty model.**

   Plan lines 87–93 leave `llm_json_mode` as an arbitrary string and provide no bounds for token/timeout settings or validation for the base URL. A whitespace-only model passes “is set”; negative/NaN/infinite timeouts, nonpositive tokens, blank/invalid URLs or malformed credentials can fail during client construction or first use instead of producing a controlled unavailable assistant. `build_container` runs inside startup (`interfaces/api/main.py:82`), so eagerly raising there can take uploads and saved-mapping replay down with the optional assistant. Missing a key must remain valid for local configurations; lack of a hosted credential must not become an application startup dependency.

   **Fix:** Add an infrastructure configuration-validation boundary with enumerated JSON modes, finite positive timeouts, positive integer token limits, nonblank model and absolute HTTP(S) URL validation. Document handling of surrounding whitespace and credential-bearing URLs. Convert invalid assistant-only configuration to an unavailable adapter with fixed variable-name diagnostics while preserving normal startup; do not indiscriminately swallow unrelated database/startup errors. Extend `UnavailableMappingAssistant` to support the missing/invalid-setting reason, since its current constructor only accepts a provider. Test blank/invalid settings, unknown provider, explicit fake and keyless local mode, with a transport spy proving health, prepare, upload, preview and saved replay make no provider calls. Isolate tests from real environment variables: `_env_file=None` alone does not disable environment loading in `tests/interfaces/test_api_assistant.py:25`.

9. **P2 — Client construction, ownership and shutdown are missing from the wiring design.**

   Plan §1 requires `OpenAICompatibleAssistant(settings, client)`, but §4 does not say who builds or closes that client. Constructing it directly in `interfaces/api/container.py` would put an `httpx2` import outside infrastructure, contrary to the requested boundary. A persistent injected client also has no shutdown hook in the current `Container` or lifespan, which simply yields (`interfaces/api/main.py:82–84`). Constructing one on every attempt instead can leak sockets if ownership is left implicit.

   **Fix:** Define an infrastructure factory/default-client path so the interface composition root imports only the adapter/factory and application port, with a synchronous client compatible with the existing synchronous `complete`. Choose explicit ownership: close owned clients in an infrastructure-managed scope or expose application-neutral cleanup to lifespan; never close a caller-owned test client unexpectedly. Keep `httpx2` types/exceptions out of ports, DTOs and use cases. Run Ruff, mypy and import-linter in completion checks. The current forbidden-module contracts explicitly protect domain/application, but do not themselves prohibit a direct interface import of `httpx2`; add an appropriate direct-import guard if that infrastructure-only policy is to be mechanically enforced without prohibiting normal composition-root imports of infrastructure.

10. **P2 — The literal request-body assertion does not establish the verbatim guarantee.**

    Plan lines 22–24 require the request body to contain `prepared.text` byte for byte. JSON transport escapes quotation marks, backslashes and control characters, so the raw HTTP body normally cannot contain the original JSON text as a byte substring. The local `httpx2.Request` probe confirmed that substring assertion fails even though decoding the outer JSON recovers exactly the original content. A weaker substring check on decoded content could instead allow an extra prefix, suffix or new evidence.

    **Fix:** In the MockTransport handler, decode only the outer request JSON, select the exact data-message slot and assert `content.encode('utf-8') == prepared.text.encode('utf-8')`, matching length and SHA-256. Compare against the text returned by the actual prepare API on initial, negotiation/retry and repair requests. Assert complete message roles/order and that only the specified repair fields are appended. Include Unicode, escaped newlines/quotes/backslashes and exact large-number/decimal spellings to catch reparsing/re-serialising `prepared.document`. Pin the fixed preamble and repair instruction to `PROMPT_VERSION` in `application/assistant_contract.py`, with an explicit version-bump/stale-digest regression when either changes.

11. **P2 — Repair material is not explicitly covered by the data-only instruction.**

    Plan lines 35–48 replay candidate text as an assistant turn and append issues directly to an instructional user turn. The quoted system rule covers “the data message,” which is the prepared-context message, but does not explicitly mark either new repair field as untrusted data. Sanitisation removes exposure patterns, not embedded instructions; both the model's previous candidate and validator messages derived from it can contain instructions. The merged #13 revision 3 and `application/ports.py` require repair material to remain data too.

    **Fix:** Extend the fixed, versioned system/repair instructions to explicitly cover the prior assistant candidate and the delimited issue block: they are untrusted artifacts to correct, never a source of instructions that overrides the task. Retain the application's existing sanitized bounded strings without fetching new evidence or reinterpreting embedded roles. Add a repair request containing synthetic role delimiters and “ignore previous instructions” text, and assert exact placement and the fixed data-only warning in the transport request. This tests the intended boundary, not a claim that prompt injection becomes impossible.

12. **P2 — The recording strategy requires unavailable live access and does not distinguish fixtures from evidence.**

    Plan lines 97–121 require a newly captured “real OpenRouter reply,” an invalid/valid recorded pair and a PR live run. This checkout has neither network access nor credentials, and contains no proposed `llm_recordings` corpus. MockTransport cannot create live provenance. Body-only recordings also cannot drive status/header behavior such as JSON negotiation and `Retry-After`; connection failures/timeouts must be simulated as exceptions. Labeling fabricated fixtures as OpenRouter/LM Studio/Ollama recordings or placing them in “Tested configurations” would violate ADR-005's evidence rule.

    **Fix:** Make implementation and deterministic CI runnable with committed, explicitly labelled synthetic protocol fixtures, or reuse independently supplied real recordings with provenance. Store status, selected non-sensitive headers and response body separately from provenance (synthetic versus captured, date, endpoint/server version, model, prompt version and fixture/context digest). Inject transport exceptions in code, and prohibit test fall-through to real HTTP or reading real keys. Implement but do not run the smoke/capture tool here; keep sample sending opt-in and its output bounded and secret-safe. Record live verification as pending, with an executable procedure for a later authorised environment. Only later captured runs can populate “Tested configurations”; retain #16's two-distinct-model release gate. Clarify ADR-005's “CI uses the fake adapter only” wording to permit deterministic compatible-adapter tests over MockTransport while keeping real provider access forbidden.

13. **P2 — Documentation scope omits the changed failure and operational contracts.**

    Plan §6 proposes updating only `503` variants in `docs/api/v0.1.md`. Its introductory claim that refused responses fail after repair is already inconsistent with #13's terminal refusal behavior. The API also currently describes transport failure details with `attempts`, while `_call` actually returns only `[{"kind": ...}]` for adapter errors (`assistant.py:326`). New negotiation/retry/timeout behavior cannot be understood from four environment variables and a model-switch instruction alone.

    **Fix:** Add a complete documented outcome table: refusal → `200`/null/no repair; length or malformed generated envelope → one repair then `502` if still unusable; invalid mapping after repair → editable `200` draft; malformed transport/timeout/provider error → terminal `502`; unavailable configuration/authentication/connection → `503`. Document actual error-detail fields and distinguish application attempts from transport attempts. In the planned `docs/llm/configuration.md` and `.env.example`, include all new settings, defaults/bounds, URL roots retaining `/api/v1` or `/v1` exactly once, local model prerequisites, optional OpenRouter-header values/configuration, timeout and retry semantics, JSON-mode limitations and troubleshooting. Include offline test/smoke commands, pending-versus-tested evidence, the fixed preamble plus derived repair exposure, and the limitations of redaction. Model/server compatibility must be attached to evidence rather than inferred from sharing `/chat/completions`.
