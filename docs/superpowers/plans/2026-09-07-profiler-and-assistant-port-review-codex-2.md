1. **P1 — First-pass finding 1: partially resolved. The digest binds the final sanitized text, not all the inputs the plan claims it binds.**

   Plan lines 104–141 now define request-specific preparation, a recording-adapter check and a versioned fixed preamble. Recomputing deterministic content and comparing its digest is a valid way to bind the displayed data context. However, sanitization and trimming are many-to-one: two different email messages can both become `<email>`, and changing a discarded history turn does not change the final text. More seriously, two different requested names can sanitize identically while `RunAssistant` stamps the different original names into the result at lines 159–160. `include_sample` is not explicitly in the serialized document; a request whose samples are all dropped can also lose that distinction. Thus “any change” invalidates the digest at lines 128–130 is false. The version fields listed in prose also need an explicit representation in the document schema. A plain SHA-256 supplied by the client establishes matching-content acknowledgement, not proof that the client fetched the prepare response, as claimed at lines 134–135.

   **Fix:** in the planned preparation use case and `application/dto.py`, distinguish the payload digest from a binding over the complete validated request, including sample opt-in, identity, current mapping, message/history and all relevant versions. Keep any binding of unsanitized inputs server-side or authenticated/opaque rather than exposing those inputs. Alternatively, explicitly adopt content-equivalence semantics and ensure no behavior depends on inputs excluded by sanitization or trimming. Make `context_sha256` required for every run if every call must use two steps; lines 132–133 currently specify the missing-digest case only for samples. In `interfaces/api/schemas.py` and `docs/api/v0.1.md`, state exactly what acknowledgement establishes. Test redaction-equivalent names/messages, trimmed-history edits, all-samples-dropped opt-in, prompt/policy changes and missing digests for both request kinds. Repair needs its own treatment under finding 13.

2. **P1 — First-pass finding 2: partially resolved. Full-value ordering is fixed, but sensitive keys and outgoing counts still fall outside the stated guarantee.**

   Plan lines 68–72 and 98–100 correctly sanitize before clipping and include mapping notes, messages and history. Restricting client roles and enclosing their content as data is also an improvement. But lines 89–94 now mandate that keys are never redacted. A trace key containing an email or credential is still disclosed in sample objects; an unaddressable key is copied literally into the profile at lines 46–48. Conversely, applying the generic string sanitizer to its profile path or a DSL path can rewrite the string while leaving the source key unchanged. Merely documenting this does not implement the original requirement to handle sensitive field names without silently rewriting executable paths. Cached sanitized examples, another sanitizer pass, and subsequent sample/history removal also make “counts per outgoing document” ambiguous: neither recounting placeholders as zero nor retaining counts for removed content is accurate.

   **Fix:** define a schema-aware policy in planned `domain/redaction.py` and the context builder: classify sensitive source keys before exposing paths, withhold affected fields/subtrees or require explicit disclosure acknowledgement, and report omissions using safe locators. Preserve executable path syntax rather than substituting inside it. Carry bounded redaction provenance through cache and trimming so final counts describe retained content. Test secrets in addressable/unaddressable keys, paths and enum-map keys, repeated sanitization, and redacted records removed by the budget. The fixed preamble must explicitly treat client history and repair text as untrusted data; a test that text merely remains a string does not establish that boundary.

4. **P2 — First-pass finding 4: partially resolved. Removing generic entropy rules helps IDs, but the replacement rule list is not yet precise enough to review.**

   Plan lines 76–89 remove the demonstrated base64/hex collision and lines 265–267 add the right negative-case categories. However, only some replacement patterns are concrete. GitHub/Slack suffix lengths, Google `AIza…`, JWT boundaries, assignment syntax, and IPv4/IPv6 token boundaries remain unspecified. An implementation based on substring matching could redact a dotted identifier such as `call_10.20.30.40`, or colon-separated time text as an IP-like fragment. These are risks from unspecified patterns, not measured false positives from an implemented redactor. Keeping generic opaque IDs also requires an explicit residual-exposure policy; it does not imply arbitrary opaque credentials are detected.

   **Fix:** include a reviewed pattern/recognizer table in the plan and planned redaction module, with lengths, alphabet, boundaries, case behavior, overlap handling and replacement scope. Validate IP candidates as complete address tokens with `ipaddress`; define loopback exceptions precisely. Keep known credentials redacted under ID-like keys. Add exact negative strings from the checked-in TraceLab fixture and synthetic SWE-shaped cases, plus near-prefix IDs, timestamps, dotted IDs and valid credential positives. State the unsupported opaque-secret case in `docs/mapping/README.md` rather than promising comprehensive detection.

5. **P2 — First-pass finding 5: partially resolved. The trimming sequence does not enforce the advertised 64 KiB maximum or bound all preprocessing.**

   Plan lines 60–64 bound profiler traversal and lines 123–127 trim samples, examples, then history. But there is no terminal action if the remaining profile, current mapping, message or omission report is too large. A compact illustrative profile with 400 legal 199-character keys, only `path/records/values/nulls/examples`, and no examples is **104,011 UTF-8 bytes** using the existing exact codec. It meets the path/key limits and cannot shrink under any listed step. An oversized mapping has the same problem. The recursive sanitizer and sample copying are not assigned the profiler's node/depth limits; traversing an entire large source array before rejecting it still bypasses the intended work bound. Nor are retained distinct strings or literal unaddressable keys bounded in bytes.

   **Fix:** give the context builder a terminating policy: trim optional evidence, then return a documented `413 context_too_large` if indispensable content cannot fit. Count final UTF-8 bytes including redaction/truncation metadata. Reconsider dropping all samples before redundant examples and old history: define evidence priorities, preserve the latest user instruction and current mapping, and report when no sample remains. Bound request bytes, sanitizer traversal, sample projection, distinct-state bytes and omission reporting before allocating full recursive copies; perform full-value classification before shortening retained scalar values. Test the profile-only counterexample, oversized mapping, long keys, deep client history and wide sample arrays in the planned profiler/context tests and `interfaces/api/schemas.py`. No port call may occur on exhaustion.

7. **P2 — First-pass finding 7: partially resolved. Observation denominators improve, but wrapper nulls, integral decimals and capped distinct hints are still inconsistent.**

   Plan lines 33–39 separate record coverage from value-level null rates. However, “a wrapper whose `value` is null” does not cover production binary wrappers (`base64`) or duration/time wrappers (`seconds`): see `backend/src/agentscope_app/infrastructure/readers/parquet.py:266–280`. Using `.get("value")` would count every such wrapper as null; requiring a literal `value` member would miss actual nulls. Integral `Decimal` values have no explicit type under lines 40–42: they are not Python `int`, and `number` is restricted to non-integral Decimal. The reader returns integral Decimal floats too (`parquet.py:256–263`). Finally, a distinct count saturated at `">50"` cannot support a `distinct / values > 0.9` identifier decision for 2,000 observations. Traversal exhaustion also leaves some paths unobserved, which should not be reported as known absent.

   **Fix:** define a wrapper-kind-to-value-member table and integral numeric classification in planned `domain/profile.py`; distinguish incomplete observation from absence and specify zero-denominator rates. Base high-cardinality hints on a declared bounded estimator/sample, or return an unknown hint after exact state saturates. Keep exact example/min/max values in the textual API representation. Extend tests to non-null/null binary, duration and time wrappers, `Decimal("1")`, saturated unique and repeated IDs, and records cut short by node limits.

8. **P2 — First-pass finding 8: partially resolved. Identity is carried, but the stamping policy can silently relabel incompatible output.**

   Plan lines 109–118 carry name/source and distinguish DSL and target versions. Lines 159–161 nevertheless say input format and both versions are stamped “from the request,” although `AssistantRequest` has none of those fields. Blindly overwriting an incompatible proposed version or a revised mapping's format bypasses the rejection required by ADR-004 and `backend/src/agentscope_app/domain/mapping/parser.py:104–127`. Revise also lacks a policy for disagreement between requested identity and `current_mapping`. The outgoing `target` lists versions/entities but does not specify where the complete DSL grammar and target field requirements reach the adapter; a version number alone is insufficient for an unfamiliar model.

   **Fix:** define an authoritative resolved contract in `application/dto.py`: upload-derived format, server-supported DSL/target versions, required target fields and the DSL schema/reference, whether in prepared data or the versioned preamble. Validate revise identity/format before preparation. Stamp permitted identity fields deliberately, but reject/repair incompatible supplied versions and formats rather than silently relabeling them. Add tests for version 2 output, wrong input format, inconsistent revise identity and missing contract metadata alongside the planned non-default-name test.

9. **P2 — First-pass finding 9: partially resolved. Repair ownership is explicit, but terminal states are not.**

   Plan lines 149–175 provide an explicit repair request, two-call ceiling, failure kinds and the correct distinction between parsing and preview. But length-finished output triggers repair while the second result is “validated the same way and returned with its issues either way.” A length-finished response can contain parseable mapping JSON; `parse_mapping` cannot establish whether generation was complete. The plan must explicitly prevent that candidate becoming executable after the second attempt. An adapter may also raise `AssistantError(malformed)`, while the application repairs malformed JSON; it is unclear which malformed failures consume the second call. Valid JSON with a wrong envelope (`[]`, `mapping: null`, missing explanations) has no specified validation path.

   **Fix:** put a complete transition table in the planned run use case and `application/dto.py`: gate on finish status before considering executability, distinguish response-envelope failure from mapping invalidity, and define repair eligibility for every reply/error kind on both attempts. A terminal `length` or refusal must never yield an executable proposal, even with parseable JSON. Bound and sanitize all diagnostics, not only `raw_text`. Extend scripted tests to every terminal state on the second call and exact call counts for both propose and revise. Resolve the return/status contradiction in finding 16.

11. **P2 — First-pass finding 11: partially resolved. Migration/save policy is specified, but cache invalidation and allowed writes still contradict the preparation flow.**

    Plan lines 213–233 now define nullable cache columns, repository methods, explicit user saves, immutable revisions, idempotence and accurate existing preview storage. However, the cache stores already-sanitized examples and is invalidated only on profiler version. A sanitizer-only change cannot recover examples previously replaced or clipped; sanitizing that cache again is not equivalent to recomputing under the new policy. Adding a sanitizer version to the context digest alone does not repair the cache. Preparation “computing [the profile] if needed” at lines 114–115 conflicts with `ProfileFile` caching and the blanket no-write claim for prepare/run at lines 229–231. Row counts cannot detect an UPDATE of `uploads.profile` or a mutation to an existing mapping.

    **Fix:** in migration `0004_upload_profile`, `UploadRepository` and planned `ProfileFile`, use a cache fingerprint covering reader representation, profiler, sanitizer and effective limits; recompute from raw bytes when it changes. An aggregate integer version is acceptable if its bump policy explicitly covers all these inputs. Choose either allowed cache-only writes during preparation/run, or a pure computation path on cache miss, and document that choice consistently. Test nullable-cache upgrade, sanitizer-only invalidation after restart, cold-cache prepare/run and version changes. Compare persisted values or capture writes, rather than relying solely on table row counts, for no-write assertions.

13. **P1 — New: `RepairRequest` bypasses the prepared, sanitized and bounded context boundary.**

    Plan lines 136–139 allow only fixed instructions plus verbatim prepared data, but lines 149–156 add arbitrary candidate text and validation issues as a separate port input. The second call consequently has model-visible data absent from the prepared text/digest. Neither argument passes through the complete-context sanitizer or the 64 KiB budget; the 32 KiB cap at line 168 applies only to returned diagnostics. Model output and parser issues can contain credential-shaped strings and instruction-like content, including values/keys quoted by `domain/mapping/parser.py:90–117`. This is a concrete hole even if no additional source sample is introduced during repair.

    **Fix:** extend planned preparation/port DTOs with a server-owned repair representation whose candidate and issues are sanitized, bounded and explicitly treated as data. Define whether the initial acknowledgement authorizes one derived repair using only the already-approved evidence, or whether a second preview is required; do not claim the first digest previews all later model-visible text. Keep original approved data immutable, forbid new raw sample retrieval during repair, and give the entire second request an explicit budget including repair additions and preamble. Recording-adapter tests must inspect both calls, with oversized candidates, credential-bearing issues and prompt-like candidate content.

14. **P2 — New: the single-method port changes ADR-005's return contract without acknowledging the change.**

    A single `complete` method with `kind` in the prepared context is provider-neutral and can serve propose and revise. The problem is its return type: plan lines 149–158 return raw `AssistantReply.text` and move parsing of `{mapping, explanations, ambiguities, questions}` into the application. ADR-005 lines 22–26 explicitly require the port to return an application-owned `MappingProposal`, and lines 53–59 assign malformed-response handling to the adapter. An application-owned raw-text wrapper avoids vendor types but still changes this accepted boundary, despite plan line 10 claiming the ADR fixes the port shape.

    **Fix:** either return a typed application-owned candidate/proposal result from `MappingAssistant.complete`, with explicit refusal/truncation/malformed variants, leaving mapping-domain validation and the two-call repair counter in the application; or explicitly propose an ADR-005 amendment explaining why response-envelope parsing moves inward. Align `application/ports.py`, `application/dto.py`, fake behavior and #14's adapter contract with the selected ownership before implementation.

15. **P2 — New: suppressing all wrapper children removes the evidence needed to generate correct Parquet field access.**

    Plan lines 42–44 classify wrappers by kind and prohibit profiling their children; scalar-only examples at lines 52–54 do not specify an alternative wrapper representation. Yet the fakes require timestamp unit/timezone metadata and choose `created_at.iso` or `timestamp.iso` at lines 182–189. With profile-only defaults, the compatible adapter gets neither those addressable children nor a defined rule explaining them. Production time/duration values use `.seconds` regardless of the storage unit, and binary uses `.base64` (`backend/src/agentscope_app/infrastructure/readers/parquet.py:266–297`). Guessing `.value` or treating storage units as the unit of `.seconds` produces missing paths or incorrectly scaled mappings.

    **Fix:** retain logical wrapper classification but add bounded, sanitized wrapper metadata and explicit executable accessors to the profile contract, or include a versioned wrapper contract in the adapter-visible target/reference. Report observed unit/timezone variants, logical nulls and safe accessor examples without double-counting wrapper children as independent source observations. Test generation and parser/interpreter behavior from profile-only timestamp, duration, time and binary records; do not let fake hardcoding hide information missing from the common port input.

16. **P2 — New: API outcome/status rules conflict and the new errors need explicit envelope integration.**

    Plan lines 164–171 promise the second candidate with issues and define `MappingProposal.executable: bool`; lines 244–245 instead return `proposal: null` for a still-invalid draft. That discards the structured editable draft required by ADR-004, leaving only capped raw diagnostics. Malformed-after-repair is a `502`, but second-attempt `length` is not assigned a status. The intended `400/409/502/503` choices are otherwise workable; no status change is required merely because a timeout uses `502`. However, the existing handler maps `ApplicationError` to `400` by default and requires `code/message/details` (`backend/src/agentscope_app/interfaces/api/main.py:38–44, 84–90`). Returning `AssistantOutcome` with a non-2xx status would violate `docs/api/v0.1.md:159–167`; a new exception not integrated with the handler could instead yield a generic 500.

    **Fix:** define one API matrix in the plan and `docs/api/v0.1.md`: `200` with an editable non-executable candidate and issues for structurally usable invalid drafts; `200` with no candidate for refusal; explicit terminal statuses for malformed/truncated replies and transport failures. Map assistant failures and stale context through `application/errors.py`, the ordered status mapping in `interfaces/api/main.py`, and `ErrorResponse` in `interfaces/api/schemas.py`. Preserve `{error: {code, message, details}}` for every non-2xx response, carrying bounded safe diagnostics in `details`. Include unknown uploads, malformed bodies/digests, oversized context, second-call failures and invalid/idempotent saves in route tests.

17. **P2 — New: relocating the codec must not silently change existing mapping content hashes.**

    Plan lines 119–120 require sorted exact serialization and lines 209–218 move `content_hash` alongside the codec, but do not define compatibility with persisted hashes. Today `backend/src/agentscope_app/infrastructure/mappings/bundled.py:20–22` hashes recursively sorted compact `json.dumps`, while `infrastructure/jsonx.py:15–17, 42–53` preserves dictionary insertion order and emits a space after each colon. These produce different bytes for the bundled document; moving functions unchanged is safe, replacing the hash serializer with the exact codec is not automatically safe. A changed digest causes an unchanged bundled mapping to be inserted as another revision on restart, contradicting idempotence. The nullable profile migration does not address this.

    **Fix:** specify separate canonicalization contracts for prepared-context digests and existing mapping identity hashes. Preserve legacy mapping hash bytes for already-supported documents when relocating `content_hash`; define exact numeric handling for newly supported Decimal values explicitly. If changing mapping hashes is intentional, design a compatibility lookup/migration that preserves IDs and historical import bindings. Add an upgrade test seeded with the current loader's stored hash, restart through the new loader and API save, and assert unchanged mapping ID/revision and no extra row. Also test recursive key-order independence for context hashes; the current codec has no sorting option.

18. **P2 — New: making revision saving public exposes races that the sequential bundled-loader policy does not handle.**

    Plan lines 216–218 use `1 + max(same name)` and a hash precheck. Two concurrent API saves can both choose the same revision, or both miss the same content hash. `backend/src/agentscope_app/infrastructure/db/models.py:96–98` enforces unique content hashes and `(name, revision)`, while `SqlAlchemyMappings.add` at `infrastructure/db/repositories.py:136` does not translate an integrity failure. The new endpoint can therefore return an unhandled 500 instead of its promised existing-record `200` or successful revision `201`.

    **Fix:** specify transactional conflict handling in planned `SaveMappingRevision` and its repository/UoW implementation. On a hash race, roll back and return the winning immutable record; on a revision-allocation race, retry allocation within a bounded policy or return a documented conflict in the standard envelope. Add concurrent identical-document and distinct-edit saves to persistence/API tests, asserting unique immutable revisions and preserved import bindings.
