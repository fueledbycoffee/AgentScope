# HTTP API contract for the day-1 thin slice (v0.1)

This is the interface the web app and the backend agree on for issues #5, #6
and #7. The backend implements it under `/api`; the web app consumes it. Field
names are final for v0.1; new fields may be added, existing ones are not
renamed. All timestamps are ISO-8601 UTC strings. Measures are integers or
`null` (never zero for missing). Every list endpoint accepts `limit` (default
50, max 500) and `offset`.

## Upload and preview

`POST /api/uploads` — multipart form, field `file`. Stores the bytes immutably.

```json
{
  "upload_id": "upl_01J...",
  "filename": "tracelab-sample.jsonl.gz",
  "sha256": "d044a766…",
  "size_bytes": 681057,
  "format": "jsonl",
  "record_count": 4770,
  "preview": [{"locator": "line:1", "payload": {"provider": "claude", "session_id": "…"}}],
  "already_imported": [{"import_id": "imp_…", "imported_at": "2026-09-07T10:00:00Z"}]
}
```

`format` is `jsonl` or `parquet` (gzip is detected). `preview` holds the first
20 records; an entry that could not be decoded has `"payload": null` and an
`"error"` string. `already_imported` lists earlier imports of the same bytes.

## Mappings

`GET /api/mappings` → `[{"id": "map_…", "name": "tracelab-v1", "source": "tracelab", "revision": 1, "created_by": "bundled", "input_format": "jsonl"}]`

`GET /api/mappings/{id}` → the mapping record plus `"document": {…DSL v1…}` and
`"issues": []` (validation issues of the document, each `{stage, path, code, message, severity}`).

`POST /api/mappings` body `{"document": {…DSL v1…}}` → `201` with the mapping
summary plus `"created": true` when the document is new; `200` with
`"created": false` and the existing record when the same document (by content
hash) was already saved; `400 invalid_input` with the validation issues as
`details` when the document is not executable (only executable revisions are
stored, because saved mappings replay without any assistant). A changed
document under a known name becomes the next revision of that name;
revisions are immutable and imports keep their `mapping_id`. Saves by the API
carry `created_by: "user"`.

`GET /api/mappings/schema` → the mapping DSL v1 JSON Schema (static), for
client-side shape checks in the assistant UI.

`POST /api/mappings/validate` body `{"document": {…}}` → `{"issues": [...],
"executable": bool}`: the validation issues a save would report, without
saving anything.

## Mapping assistant (ADR-005)

The assistant never sees a file: it sees a **prepared context**, a JSON
document the server builds from the bounded, redacted field profile of an
upload, and the client has to fetch that exact text before it can be sent.

`POST /api/uploads/{id}/profile` → `{"upload_id", "cached": bool, "profile": {…}}`.
The profile is computed once per upload and cached on the upload row
(`cached: true` afterwards; recomputed when the profiler or redactor version
changes). It inspects at most 2,000 records; `profile.truncated` names every
limit that applied (`records`, `paths`, `depth`, `array_items`, `nodes`,
`distinct`, `unaddressable`, `withheld`). Each field carries `path` (a DSL v1
path), `selector`/`relative` (for array elements), `records`/`missing`
(records with and without the path), `values`/`nulls` (values observed, one
per array element), `types`, `distinct` (exact up to 50, then
`distinct_capped`), up to five redacted `examples` (strings cut to 80
characters after redaction), exact `min`/`max`, `min_length`/`max_length`,
`hints` (`iso8601`, `epoch_seconds`, `epoch_millis`, `uuid`, `identifier`,
`enum`, `free_text`, all computed from values) and, for Parquet wrappers,
`wrapper: {kind, units, tz, accessors}`. Keys the grammar cannot address are
listed under `unaddressable` (`{parent, key, reason}`); keys the redactor would
change are `withheld` with their whole subtree (`{parent, reason}`, never the
key). `404` for an unknown upload.

`POST /api/assistant/prepare` body:

```json
{"kind": "propose" | "revise", "upload_id": "upl_…",
 "identity": {"name": "my-mapping", "source": "my-source"},
 "include_sample": false,
 "current_mapping": {…}, "message": "…", "history": [{"role": "user"|"assistant", "content": "…"}]}
```

→ `{"kind", "context_sha256", "bytes", "payload_text", "payload", "redactions": {reason: n},
"truncated": {step: n}, "sample_included", "sample_count"}`. `payload_text` is
the exact UTF-8 text the adapter will send as data (the adapter adds only a
fixed, versioned instruction preamble with no upload content); `payload` is
the same document parsed; `context_sha256` is the SHA-256 of `payload_text`.
The document carries the identity, the upload's format, every version
(`context`, `prompt`, `profiler`, `sanitizer`), the target contract (entities,
required fields, a DSL reference), the profile, `sample_included` and
`sample_count`, and, when present, the redacted `sample` (at most 20 records
chosen to cover every path, projected to depth 8 and 20 array items),
`current_mapping`, `message` and `history`. Everything is passed through the
redactor first (private keys, credentials, URL user info, e-mails,
home-directory paths, IP addresses, text over 200 characters); `redactions`
counts what was replaced in the retained content. The text is trimmed to
the configured budget (`AGENTSCOPE_LLM_CONTEXT_BYTES`, 64 KiB by default) in
this order, each step recorded in `truncated`: sample records from the end
(`sample_dropped`), examples down to two per field (`examples_reduced`),
history oldest first (`history_dropped`), examples removed
(`examples_removed`), then nested fields left out deepest and rarest first
(`fields_omitted`, with `profile.omitted` counting them per parent path so the
model knows what it did not see); `$` and top-level fields are never omitted.
If that is not enough the request fails with `413 context_too_large` (details:
`bytes`, `limit`, `truncated`, `fields`) and nothing is sent.
`include_sample` defaults to false (profiles first); `revise` needs
`current_mapping` (whose `name`/`source` must equal `identity`) and `message`;
`message` is at most 4,000 characters, `history` at most 20 turns of 4,000;
`name` and `source` may not contain anything the redactor would rewrite. `400
invalid_input` with `{field, message}` details otherwise.

`POST /api/assistant/run` body: the same as `prepare` plus `"context_sha256"`
(required for every run). The server prepares the context again from the same
inputs and compares digests: `409 stale_context` when they differ (the client
must prepare again). What the digest establishes is that the client fetched
exactly the text that is sent, not that a person read it; sanitisation and
trimming are many-to-one, so two requests that produce the same text share a
digest by design. On success → 

```json
{"proposal": {"mapping": {…}, "explanations": [{"target", "path", "why", "confidence"}],
              "ambiguities": [{"target", "options", "what_settles_it"}], "questions": [],
              "model": "…", "executable": true} | null,
 "issues": [{stage, path, code, message, severity}], "attempts": 1 | 2,
 "diagnostics": {"finish", "model", "raw_text", "failure", "context_sha256", "sample_included"}}
```

`mapping.name`, `mapping.source` and `mapping.input_format` are always the
request's identity and the upload's format (the model cannot rename or
retarget a mapping); versions are validated, not rewritten. `executable`
means the document passes the mapping contract, not that it fits the records:
preview it next. At most two generation calls happen per run: a reply that is
cut off (`length`), not a JSON object with a `mapping` object, or a
non-executable mapping gets **one** repair call carrying a redacted, bounded
copy of the model's own reply and the validation issues, as data. Outcomes:
`200` with an executable proposal; `200` with a non-executable proposal and
its `issues` (an editable draft) when the repair did not fix it; `200` with
`proposal: null` and `diagnostics.failure: "refusal"` when the model refused;
`502 assistant_failed` with `details: [{"kind": "truncated" | "malformed" |
"timeout" | "provider", "attempts": n}]` when no usable reply came back
(`attempts` counts generation calls, 1 or 2, not HTTP attempts); `503
assistant_unavailable` when the assistant is not configured, the provider has
no adapter, the endpoint refuses the credentials or cannot be reached (the
message names the variable to check; `AGENTSCOPE_LLM_PROVIDER=fake` selects the
deterministic fake, `openai_compatible` any chat-completions endpoint, see
`docs/llm/configuration.md`). A candidate born from a cut-off reply is never
`executable`. `raw_text` is redacted and capped at 32 KiB; `diagnostics.model`
is the model the endpoint reported and `diagnostics.adapter_notes` lists
adapter events (for example `json_mode_off_after_rejection`). These routes
write nothing except the profile cache; saving a proposal is the explicit
`POST /api/mappings` above.

Outcome table, in one place:

| What happened | Status | Body |
| --- | --- | --- |
| executable proposal (first or second attempt) | 200 | `proposal.executable: true` |
| still not executable after the one repair | 200 | `proposal.executable: false`, `issues` |
| the model refused (first or second attempt) | 200 | `proposal: null`, `diagnostics.failure: "refusal"` |
| cut off or not a JSON object, twice | 502 | `assistant_failed`, `kind: truncated \| malformed`, `attempts: 2` |
| transport shape, timeout or provider failure on either attempt | 502 | `assistant_failed`, `kind: malformed \| timeout \| provider`, `attempts` |
| not configured, no adapter, bad credentials, unreachable | 503 | `assistant_unavailable` |
| the digest no longer matches | 409 | `stale_context` |
| over 64 KiB after trimming | 413 | `context_too_large` |

## Import

`POST /api/imports/preview` — body `{"upload_id": "…", "mapping_id": "…", "sample": 200}`.
Runs the mapping on the first `sample` records without persisting. Cross-file
claim diagnostics are computed only on commit, not in this sample preview.

```json
{
  "records": {"accepted": 190, "partial": 0, "rejected": 10, "sampled": 200},
  "entities": {"session": 190, "model_call": 190, "tool_call": 240},
  "rejects": [{"locator": "line:7", "rule_id": "tool_call", "path": "tool_call[2]", "code": "invalid_value", "field": "wall_latency_ms", "message": "…"}],
  "warnings": {"absent": 12, "null": 3, "invalid_value": 1},
  "emissions": [{"entity": "model_call", "path": "model_call", "locator": "line:1", "fields": {"model": "claude-opus-4-6", "input_tokens": 16147}}]
}
```

`POST /api/imports` — body `{"upload_id": "…", "mapping_id": "…", "source": "tracelab"}`
for one file, or `{"source": "tracelab", "files": [{"upload_id": "…", "mapping_id": "…"}, …]}`
for a batch of 1 to 20 files, each bound to its own mapping revision (both
forms are accepted; the single form is the batch of one). Applies each file's
mapping to its records and writes everything in one transaction. Bindings of
the same bytes with the same mapping collapse into one file; the same bytes
under two mappings, a mapping whose `input_format` differs from the upload's
format, or giving both forms at once are `400`. A file whose bytes were
already committed for this source is skipped as `duplicate` and its records
are counted as such; when every file is a duplicate the attempt's `status` is
`duplicate`. Limits: 100,000 records and 100 MiB of file bytes to read per
attempt (duplicates excluded), else `413`.

```json
{
  "import_id": "imp_01J…",
  "status": "committed",
  "source": "tracelab",
  "mapping": {"id": "map_…", "name": "tracelab-v1", "revision": 1},
  "started_at": "…", "finished_at": "…",
  "files": [{"filename": "…", "sha256": "…", "size_bytes": 681057, "format": "jsonl", "record_count": 4770,
             "mapping": {"id": "map_…", "name": "tracelab-v1", "revision": 1}, "status": "committed",
             "records": {"accepted": 4770, "partial": 0, "duplicate": 0, "rejected": 0, "ignored": 0}}],
  "records": {"accepted": 4770, "partial": 0, "duplicate": 0, "rejected": 0, "ignored": 0},
  "entities": {"session": 80, "model_call": 4770, "tool_call": 5723},
  "warnings": {"absent": 2337, "null": 889},
  "reject_count": 0
}
```

`status` is `committed`, `duplicate` (nothing inserted) or `failed` (nothing
inserted). Each entry of `files` carries its own `mapping`, `status`
(`committed`, `duplicate`, `failed`), `records` counts and, for a `duplicate`
file, `duplicate_of`: the earliest committed import of the same bytes for this
source (`null` otherwise); the attempt-level
`mapping` echoes the first file's mapping for display only. An attempt that
lost a race with a concurrent import of some of its bytes is recorded as
`failed` (which file collided is unknown, so none is claimed as duplicate) and
the request answers `409`; retrying is safe. `error` is a string (`"ExceptionType: reason"`) when `status` is
`failed` and `null` otherwise. `records` counts source records; `entities` counts
observations emitted, which is why one record can produce several entities.
`entities` only contains the kinds that were emitted: it is `{}` for `duplicate`
and `failed` imports and may lack `tool_call` for a file without tools; treat a
missing kind as 0. `warnings` is likewise a map of the codes that occurred.

`GET /api/imports` → `[{full import report}]`, including warnings, file conditions
and comparison version, newest first.

`GET /api/imports/{id}` → the full report above.

`GET /api/imports/{id}/rejects?code=&rule_id=&file_sha256=&limit=&offset=` → `[{"file_sha256", "locator", "rule_id", "path", "code", "field", "message", "payload"}]`.
Rows carry the file they came from; `file_sha256` narrows to one file of a batch, `rule_id` to one rule.

`GET /api/imports/{id}/rejects/summary` → `{"codes": {code: n}, "rules": {rule_id: n}, "files": {sha256: n}, "outcomes": {outcome: n}}`,
the counts a rejects browser needs for its filters (one reject row per rule that refused a record, so a record can count twice) and the record outcomes of the attempt.

`GET /api/imports/{id}/records?outcome=&file_sha256=&limit=&offset=` → `[{"file_sha256", "locator", "outcome", "entity_counts", "warning_counts"}]`,
every source record's outcome, ordered by file then by locator position (`line:10` after `line:9`). `outcome` is one of `accepted`, `partial`, `duplicate`, `rejected`, `ignored` (`400` otherwise). The raw payload of a row is `GET /api/raw-records`.
`field` is `null` when the reject is not about one field (for example `invalid_json`, `internal_error`); the same holds for `diagnostics[].field` on a session.

### Cross-file claim diagnostics (comparison version 1)

Reports add `duplicate_detection_version`: `1` for newly checked committed
attempts, `null` for historical, failed or replay-only attempts. Null means
unchecked, not a known zero. Each file adds `warnings` (record warnings summed
for that file) and `claim_conditions` (an array, normally empty).

Two emission codes can occur in record, file and attempt warning maps:

- `suspected_duplicate`: another file holds the same scoped native claim, and
  **no peer file holds an equal canonical projection**.
- `matching_claim_equal_projection`: another file holds the same scoped claim
  with equal values. This takes precedence even when differing peers also exist.

Each code counts incoming emitted observations, once each, not records or pairs.
All observations, the five record outcomes, session reduction and metric totals
are retained. Thus byte-different equal re-exports still add observations, with
an explicit equal-match count. Repeated keys within one file never qualify each
other; equal re-exports of repeated keys do not become suspected duplicates.
All files in a batch participate before detection; sequential imports only add
warnings to the later attempt. Exact replay adds no new diagnostics.

Scope includes source namespace, file-local harness, entity, session external ID
and typed native-key values plus a fingerprint of their mapping extraction
(paths, transforms, defaults, policies and selectors). Mapping revisions with
unchanged key extraction compare; changing the source path of a native key does
not. Native keys with any null component are ineligible; empty string is literal.
Frozen canonical projections cover all schema-v1 fields of that entity, use UTC
microseconds and exact integers, and normalize unmapped optional values to null.
Tools do not inherit their parent's model or token values into their projection;
an inherited session ID remains part of their own scope/projection.

Harness scoping follows ADR-002 and is stricter than the current session storage
key `(source, external_id)`: different declared harnesses cannot compare, including
provider changes that change the harness. Children need an unambiguous session
harness declared in the same record, or otherwise in the same file. No session
rule still permits implicit sessions, with unavailable claim comparison.

A missing/ambiguous harness is recorded once per file/rule as
`{"file_sha256":"…","rule_id":"…","code":"claim_scope_unavailable",
"affected_emissions":150,"message":"…"}`. It is a condition, outside all warning
counters and outside per-emission diagnostics. `claim_projection_too_large` similarly
counts skipped scopes/projections exceeding 64 KiB UTF-8. No values are truncated.
Version 1 can coexist with these coverage conditions. SHA-256 projection identity
uses the same collision-resistance assumption as content-addressed file identity.

`GET /api/imports/{id}/diagnostics?code=&file_sha256=&locator=&limit=&offset=` returns:

```json
{
  "items": [{
    "file_sha256": "incoming-sha", "locator": "line:10",
    "emission_path": "model_call", "rule_id": "model_call", "entity": "model_call",
    "code": "suspected_duplicate", "message": "Another file holds this scoped native claim, but no peer file holds equal canonical values. All observations were retained.",
    "peer": {"import_id": "imp_peer", "file_sha256": "peer-sha", "locator": "line:2",
             "emission_path": "model_call", "entity": "model_call"}
  }],
  "total": 1,
  "conditions": []
}
```

Filters combine with AND. `code` accepts the two emission codes above (`400`
otherwise). Unknown import is `404`; a known empty result has `items: []`,
`total: 0`. Limits use the existing 1–500 bound, offset is non-negative.
SQL orders by file, numeric locator, locator text, emission path, entity and code.
`total` counts all matching emission diagnostics before pagination. Unlike older
list routes, this envelope supports reconciling warning totals without loading
all evidence. `conditions` is filtered by file only, not locator/code or pagination;
conditions are bounded by file/rule and are separate from `total`. Comparison version
lives on report/history, not this envelope. Peer is one stable example, including
same-attempt peers; use each side's file hash/locator with `/api/raw-records`, whose
`payload_text` preserves large numbers, and peer import ID with `/api/imports/{id}`.

Migration 0005 rebuilds eligible historical claims from stored raw records,
mappings and contribution provenance without changing observations or old warning
snapshots. Unrecoverable files are skipped with `claim_backfill_unavailable` and
an explanatory message (affected count 0 means not determined for this historical
file). Historical comparison versions remain null even when their claims were
recovered for future comparison. Missing provenance does not prevent startup.

The backend report/history carries these counts and evidence; dedicated Console
notices, filters and links are a UI follow-up. Session detail still exposes only
its existing reducer diagnostics and has no cross-file duplicate marker.

## Metrics

Definitions are versioned in `domain/metrics.py`. `GET /api/metrics/summary?source=&agent=`
retains the four existing metrics and adds `output_tokens`. Every metric, including counts,
has a unit, coverage, ID/version, exact text and trust metadata. For example, a mixed
input-token result is:

```json
{
  "value": 30,
  "definition": "Sum of recorded model_call.input_tokens; no fallback or unit conversion.",
  "unit": "tokens",
  "coverage": {"known": 2, "total": 3},
  "by_semantics": {"a": 10, "b": 20},
  "metric_id": "input_tokens",
  "version": 1,
  "value_text": null,
  "recorded_sum_text": "30",
  "comparability": "mixed",
  "reason": "Contributing accounting tags differ; use the partition values.",
  "semantics_partitions": [
    {"semantics": "a", "value_text": "10", "coverage": {"known": 1, "total": 1}},
    {"semantics": "b", "value_text": "20", "coverage": {"known": 1, "total": 1}},
    {"semantics": "unknown", "value_text": null, "coverage": {"known": 0, "total": 1}}
  ]
}
```

`Coverage` stays exactly `{known, total}`, with integer row counts. Numerator and denominator
come from the same eligible population. A ratio for 0/0 is undefined. A sum with no known
contributors has a null value; an empty count is **0**, with coverage 0/0. Measured zero is
a known contributor. No timestamp or latency fallback, unit conversion, or token inference
occurs in this layer.

`value` is a deprecated numeric alias for the sum of recorded values; for tokens it is
**not a certified comparable total**. `by_semantics` keeps its legacy `dict[str, int]`
meaning: known contributors only, with no all-null partitions. New `semantics_partitions`
includes all partitions, independent coverage and exact decimal text. Only metric and
partition values need text; coverage counts remain integers. `recorded_sum_text` is the
exact but potentially incomparable recorded sum. Session `input_tokens` uses the same
shape, definitions and accounting rules; session row counts are computed by the shared
query layer rather than cached all-time counters.

Canonical `value_text` is authoritative for exact display. Accounting status is one of:

- `not_applicable`: counts and non-token measures; no equivalent-workload claim.
- `comparable`: known token usage has exactly one non-unknown accounting tag.
- `mixed`: known usage spans multiple validated tags; canonical value is null.
- `unknown`: contributing usage has unvalidated accounting, or no known usage exists;
  canonical value is null. Coverage, partitions and reason distinguish these cases.

Null/empty tags normalize to `unknown` **before** grouping. Empty accounting is an explicit
measure-specific unvalidated value, not a global empty-string rule. All-null foreign-tag
partitions affect coverage but do not make known usage incomparable. Session detail's
`model_calls[].token_semantics` remains the raw stored value for provenance, so a raw
null/empty tag may appear as `unknown` in metric partitions.

On the TraceLab fixture the default input-token total is mixed. The Overview must display
partition values and the reason, rather than an unqualified `Unavailable`. Reserve
`Unavailable` for sums without known usage. Chart geometry may approximate exact strings;
labels/tooltips must preserve the original text. No default top-N truncation or invented
zero-filled usage is returned.

### Definitions and query routes

`GET /api/metrics/definitions` returns an array of definitions with `id`, `version`, `label`,
`description`, `grain`, `operation`, `field`, `unit`, `formula`, `scope`, `null_handling`,
`coverage_field`, `semantics_field`, `comparability_rule`, `population`, and
`supported_dimensions`. Initial IDs:

`sessions`, `model_calls`, `tool_calls`, `input_tokens`, `output_tokens`, `cache_read_tokens`,
`cache_creation_tokens`, `reasoning_tokens`, `tool_wall_latency_ms`,
`tool_internal_latency_ms`, `unlinked_tools`, `missing_usage`, `unknown_timestamps`,
`imports_in_scope`.

`GET /api/metrics/query?metric_id=input_tokens&group_by=model` uses this registry. Repeated
`group_by` accepts at most two distinct supported dimensions. There is no caller-supplied
formula or SQL. Source/agent dimensions are available for session/model/tool grains;
model only for model calls, tool_name and linked only for tools, started_day for either
child grain. Imports are an ungrouped distinct count. Internal `session_id` grouping is
not an HTTP dimension.

Response structure:

```text
{
  metric_id, definition, supported_dimensions, scope, group_by,
  overall: MetricResult,
  excluded_unknown_timestamps: integer,
  buckets: [{keys: [string | boolean | null, ...], result: MetricResult, drill_scope}]
}
MetricResult = {
  value_text: string | null, recorded_sum_text: string | null,
  coverage: {known: integer, total: integer}, comparability, reason,
  semantics_partitions: [{semantics, value_text, coverage, drill_scope}]
}
```

No lossy numeric value aliases exist in query results. Ungrouped queries include one
bucket even for an empty population; empty grouped queries have no buckets. Group keys
follow requested dimension order, sort deterministically (null first), and preserve null
separately from literal `unknown`. A started_day key is an ISO UTC date string or null;
linked is a boolean. The returned `definition` contains registry metadata; its supported
dimensions are the adjacent `supported_dimensions` field.

### Shared scope and drills

Query scope parameters are `source`, `agent`, `model`, `tool`, `started_from`,
`started_before`, `import_id`, `activity_grain`, `token_semantics`, `model_is_unknown`,
`agent_is_unknown`, `timestamp_missing`, `tool_is_unlinked`, `tool_is_linked`, `usage_missing`.
The null-label and missing-time flags are explicit predicates, not fabricated source labels. Exact model/agent values cannot be combined with their null flags. Linked
and unlinked are mutually exclusive. `session_ids` is internal only (`null` means
unfiltered, empty tuple means empty scope), and is never accepted as an HTTP filter.

Source and agent filter owning sessions; session source is authoritative for all grains.
Model/usage/semantics predicates directly filter model calls; tool/link predicates directly
filter tools. Cross-grain predicates require matching siblings in the same session through
`EXISTS`. Combined model and tool filters mean **session co-occurrence**, not a claim that
the tool is linked to that model call.

Dates require timezone-aware bounds, normalized to UTC, with half-open
`[started_from, started_before)` comparisons on the current child grain's started_at. No
observed-end fallback is allowed. Session counts/drills require matching child witnesses:
model and tool predicates must each match the **same row as their own time/import bounds**.
With neither child predicate, either child grain can witness a session time range.
`activity_grain=model_call|tool_call` makes a session drill require that chart's grain,
including when there is no time bound. Sessions without children count under session-only
filters. Null child timestamps are included without a date range and form an unknown-day
bucket; under a date range `excluded_unknown_timestamps` reports missing timestamps in the
same child grain's non-time scope. Session/import counts have no direct timestamp field
and return zero for this auxiliary child-row count; query a child metric to show exclusions.

Missing-day drills set `timestamp_missing=true` and an explicit activity_grain, mutually
exclusive with date bounds. Like time bounds, missing time filters each current child grain
and each required sibling witness; activity_grain chooses the session drill witness. Known-day drills return UTC-aware midnight/next-midnight
bounds intersected with the existing range. Model/agent null drills use the corresponding
null flags; semantics drills use normalized token_semantics, including `unknown`. Every
bucket and partition drills its eligible population, including null-measure coverage rows.

Generated day drills also carry `witness_time_override`, `witness_started_from`,
`witness_started_before`, and `witness_timestamp_missing`. These are accepted query scope
parameters and must be forwarded with the drill. With an explicit activity grain and
`witness_time_override=true`, other-grain sibling witnesses retain these original time
conditions (both null bounds means unbounded). The chart grain uses the drill's day bounds
or missing-time predicate. This prevents a chart scoped to sessions with a shell tool
anywhere in the original range from losing a model-call day whose shell tool happened on
another day. Ordinary user date filters have no override and still apply the same-row
bound rule to each required witness. Override dates must be aware/increasing; missing
witness time and witness date bounds are mutually exclusive. Witness fields without the
explicit override, or an override without an activity grain, return 400.

Import scope selects observations with the recorded import ID, plus sessions with session
contributions or matching children in that import. Reconciled sessions count once.
`imports_in_scope` counts distinct import IDs from eligible child populations, plus session
contributions only under session-only scopes. Without an activity grain it unions both
eligible child populations: a model observation can count its import when a matching tool
exists in the same session. An explicit activity grain limits this union. Duplicate import
attempts with no new contributions count zero; the earlier import is never substituted.

Quality recipes: `missing_usage` selects model calls with null input_tokens;
`unknown_timestamps` selects model calls with null started_at and therefore rejects time
bounds; `unlinked_tools` selects tools with null model_call_id. Rejects remain the existing
import report/reject-summary API because pre-canonical rejected records cannot truthfully
be assigned a session drill. See [metric architecture](../architecture/metric-layer.md)
for chart recipes, batch session metrics and migration rules. #11 owns richer summary/session
HTTP scope wiring and Overview/definitions rendering; existing summary/session routes
continue to accept source/agent in this issue.

Every invalid metric request (ID, dimension, enum, date, or scope combination) returns
**400 `invalid_input`**, with `{path, message}` details, through the established error
handler. Unknown query parameters and repeated singleton parameters also return 400; only group_by
may repeat. No 422 response contract is introduced.

## Errors

Every non-2xx response, including a malformed request body or query, carries
`{"error": {"code": "…", "message": "…", "details": [...]}}`; FastAPI's own
422 shape is never returned. `400` for invalid input (a malformed request has
code `invalid_input` and `details` of `{path, message}`; a mapping with
validation errors has its issues as `details`), `404` for unknown ids, `413` for a file over 25 MiB,
a batch over 100,000 records or an assistant context over 64 KiB after trimming
(`context_too_large`), `409` for a commit that raced another import of the same
bytes, a mapping save that raced another (`conflict`) or a prepared context
that changed before it was sent (`stale_context`), `502 assistant_failed` and
`503 assistant_unavailable` for the assistant (see above).
